## What this is

Nonead DSH Desktop brings the local Web UI, Host service and plugin system of [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) into a native desktop application. The upstream source runs **unmodified** and is pinned to a specific release; the desktop shell owns windows, tray, terminal, auto-update, multiple working profiles and packaging, and **is itself mounted as a DSH plugin** through the same composition mechanism third-party plugins use.

The product is not a reimplementation of the client — it is a thin Electron host plus a complete DSH runtime:

| Layer | Location | Responsibility |
| --- | --- | --- |
| Desktop shell | Electron main process | Single-instance lock, windows and materials, tray and menus, permissions, terminal, updates, data directory, profile state |
| Host | Node-mode child process | Loads the profile patch layer, starts the upstream profile boot, serves the Web carrier, hosts third-party Host plugins |
| Web carrier | Loopback HTTP + WebSocket | Serves the official Web UI (ephemeral port by default) |
| Renderer | Sandboxed BrowserWindow | Loads the official Web UI and is identified by a native credential header |

Shell and Host communicate over exactly one child-process IPC channel. Switching a profile or mode disposes the whole Host generation and spawns a new child process; no state is cached across a generation. The renderer never receives Electron APIs — it receives the official Web UI plus an access credential generated by the shell.

## Download and install

Official installers cover Windows x64, macOS (Universal, Intel and Apple Silicon) and Linux x64 (AppImage). No extra environment is required. The Linux x64 AppImage and deb are built by the Beta channel; the stable channel only produces a runnable directory on Linux, not an installer.

| Platform | Download | Installation |
| --- | --- | --- |
| Windows x64 | [Download installer](https://www.nonead.com/software/ndsh-desktop/downloads/windows) | Run the NSIS installer and follow the prompts |
| macOS Universal | [Download DMG](https://www.nonead.com/software/ndsh-desktop/downloads/mac) | Open the DMG and drag Nonead DSH Desktop into Applications |
| Linux x64 | [Download AppImage](https://www.nonead.com/software/ndsh-desktop/downloads/linux) | Make it executable and run: `chmod +x Nonead-DSH-Desktop-*.AppImage && ./Nonead-DSH-Desktop-*.AppImage` |

Linux notes: some distributions need FUSE installed, or you can run with `--appimage-extract-and-run`. In-app update on Linux **only checks the version and never downloads an installer**; upgrade by downloading a fresh AppImage. Use the Beta channel when you need a Linux installer — the stable channel only produces a runnable directory on Linux.

Windows ARM64 is available as an **experimental build only** and is not served by the download links or in-app updates above: the shell is native arm64, but the bundled Python / Node / Office runtime is still the x64 payload (executed through Windows emulation), and the artifact has not been run on ARM hardware yet. Build it yourself with the command under [Common commands](#dev).

Step-by-step usage, profiles and plugin commands are in the [user guide](docs/user-guide.en.md); platform and scope questions are answered in the [FAQ](docs/faq.en.md).

## Capabilities

| Capability | Description |
| --- | --- |
| Native desktop shell | Single-instance lock, native windows and menus, system tray, Dock icon; window materials are capability-gated (macOS accepts `off`/`transparent` and defaults to `transparent`, Linux accepts both but always resolves to `off`, Windows only `off`) |
| Local Host management | The shell spawns the Host child process and owns its lifecycle: graceful shutdown first, `SIGTERM` after 10 s, `SIGKILL` after 5 more; installer updates require a graceful shutdown and are refused otherwise |
| Official Web UI | Binds `127.0.0.1` only, ephemeral port by default; the shell generates a 32-byte random credential per Host generation and delivers it via `x-dsh-desktop-renderer` |
| Profiles and first-run setup | Profile directories live at `$DSH_HOME/profiles/<name>`; an uninitialised profile first shows the Desktop Setup Wizard (window mode and material, plugin market, notifications, default-browser launch, web access scope) before Host starts |
| Browser and LAN access | "Open in browser" only controls whether the system browser is launched and does not change exposure; LAN access is a separate opt-in that also shows the current LAN URL |
| Built-in plugin market | DSH Community Market provides discovery / installable / installed / sources views with extensible catalog sources and reviewed adapters |
| Brand skin | `dsh-nonead-client-skin` ships with the installer and is mounted by the Profile for every profile, with no separate installation |
| Auto-update | Fixed version check against `https://www.nonead.com/software/ndsh-desktop/version` with current version, channel and a random installation id; Windows and macOS download and install, Linux only checks |
| Update experience | The update card shows release notes supplied by the version response, and the Beta channel's tray menu and native dialogs add a "view full release notes" entry; "skip this version" persists so an unattended scheduled check does not offer it again; a failed install can be retried and rolled back to any saved snapshot |
| Window and session state | Remembers window position and size; a saved position is restored only while it still overlaps a mounted display, so unplugging a monitor cannot restore the window offscreen |
| Deep links and login item | `dsh-desktop://` links are supported, for example `dsh-desktop://settings/general` opens settings directly; the launch-at-login switch reads the effective OS state |
| Environment file | Strict layered `.env` support fills in missing variables for the Host child process and never overrides the existing environment |
| Market improvements | The plugin market previews non-image media and can install a plugin by name |
| Terminal and working directory | The shell exposes terminal and working-directory capabilities as Desktop services for plugins |
| Experimental capabilities | Onboarding enables the plugin market and Computer Use by default; speech, translation, Agent Team and Ralph ship with the runtime |

<a id="security"></a>

## Security boundaries

| Boundary | Actual behaviour |
| --- | --- |
| Renderer identity | Only requests carrying the current generation credential (`x-dsh-desktop-renderer`) count as the Electron renderer; with browser access disabled every other request gets 403 and existing browser WebSockets are dropped |
| Renderer credential transport | The credential lives only in main-process and Host memory; the Host receives one line over its **private stdin** at startup and the pipe closes immediately, so it never enters the child environment, argv or a file (the old implementation used an environment variable, which same-user processes could read from process environment or a crash dump to impersonate the renderer) |
| Web access gate | When the Host has no credential it **fails closed** for browser-class requests and logs one warning instead of permitting them; the `/connect` login exchange and read-only requests are exempted in code, and Market routes need a connection credential even for reads |
| LAN access | **No authentication**: anyone on the same network who can reach the port can open DSH and operate this machine. Enable it only on fully trusted networks |
| Installer verification | The download path supports a server-published `installerSha256` and enforces it as a hard gate, but the version endpoint does not publish that field yet; until it does, Windows verifies only `ProductName` and `ProductVersion` from the PE version resource, while macOS verifies bundle identity, embedded manifest, code signature and Team Identifier; that identity check exists only in the Stable shell, whereas the Beta shell's download path checks just the installer magic bytes and size before executing it |
| Plugin misconfiguration | A patch `id` that matches nothing logs `entry not found` and is skipped; a mismatched `name` logs `name mismatch ... skipping`; but a wrong `inject` service name **does not error** — the plugin stays pending forever and the UI merely shows unexplained HTTP 4xx |

## Repository layout

The root is a Yarn `4.18.0` workspace (`nodeLinker: node-modules`) with the following members and responsibilities:

| Path | Responsibility |
| --- | --- |
| `nonead-dsh-desktop/` | Stable-channel desktop workspace: its own shell (profiles and recovery, window controls, onboarding), the Agents Anywhere bridge and Community Market adapters, Electron bootstrap and packaging |
| `dsh-plugin-desktop-beta/` | Beta-channel desktop workspace: dual Host/Client faces, Electron bootstrap, packaging and release tests |
| `dsh-community-market/` | Product and security design of the built-in plugin market, catalog provider contract, tests and build |
| `dsh-community-fabric/` | Community interoperability RFC: Manifest/Capability, Runtime/Presentation, service composition and provenance diagnostics |
| `dsh-nonead-client-skin/` | Brand skin shipped with the installer, pulled in via a `file:` dependency and not part of the root workspace list |
| `vendor/dsh-runtime/<version>/` | Vendored DSH runtime packages and `manifest.json` per channel |
| `vendor/agents-anywhere/` | Vendored Agents Anywhere bridge packages |
| `patches/` | Yarn patches for the Electron packager, pnpm, `open`, `fs-ext`, DSH subprocess and more |
| `scripts/` | Root gates and release scripts (bilingual docs, market dependency direction, vendored runtime, icons, layout, AA release) |
| `docs/` | Product documentation; `docs/evidence/` keeps measured release and installer records |
| `deepseek-harness/` | Read-only upstream submodule, pinned to `channels.beta.commit` in `upstream.json` |

**The submodule is not required for everyday development.** The runtime is vendored, so `corepack yarn install`, `build`, `typecheck`, `test`, `dev:*` and `dist:*` do not need it; only the `upstream:*` scripts (rebuild and repack the runtime) do. `corepack yarn check:layout` does verify the submodule commit and worktree, so it necessarily fails in an uninitialised clone — that is expected.

## Building from source

### Requirements

- Node.js `^22.19.0` or `>=24.0.0`
- Root Yarn `4.18.0` through Corepack (do not install root dependencies with pnpm or npm)
- Git; only needed to initialise the upstream submodule when rebuilding the runtime

```sh
git clone https://github.com/NoneadChina/Nonead-DSH-Desktop.git
cd Nonead-DSH-Desktop
corepack yarn install
corepack yarn dev:beta     # Beta workspace
# corepack yarn dev:stable # stable-channel workspace (nonead-dsh-desktop)
```

When you actually need upstream source:

```sh
git submodule update --init --recursive
```

### Common commands

| Command | Purpose |
| --- | --- |
| `corepack yarn dev:beta` / `dev:stable` | Start the development flow for that workspace (verifies the pinned `dshmarket`, prepares AA artifacts and builds the market first) |
| `corepack yarn build` | Build the market, the Beta workspace and the stable-channel workspace (also verifies the pinned `dshmarket` first) |
| `corepack yarn typecheck` | Type-check all three workspaces |
| `corepack yarn test` | Unit tests for all three workspaces |
| `corepack yarn check` | Full headless gate: layout, architecture direction, vendored runtime, bilingual docs, AA connector, per-workspace checks |
| `corepack yarn check:ci` | The chain CI actually runs: same as `check`, but the Beta workspace uses `check:ci` (drops the upstream-paused `verify:aa`) instead of rewriting the manifest inside CI |
| `corepack yarn check:layout` | Workspace topology, exact pins, submodule, vendored runtime, icons and layout gates |
| `corepack yarn check:bilingual-docs` | Verify that the Git blob hashes recorded in `*.i18n.yaml` match the documents |
| `corepack yarn check:vendored-runtime` | Verify `vendor/dsh-runtime/` against `upstream.json` |
| `corepack yarn market:prepare` / `market:check` | `market:prepare` moves `dshmarket` to npm `latest` (only the two desktop workspaces' `resolutions`/dependencies and `yarn.lock`); `market:check` is the offline consistency check every build runs, and only `--latest` reaches the network |
| `corepack yarn aa:prepare-release` / `aa:check` | Build or verify Agents Anywhere release artifacts |
| `corepack yarn package:dir:beta` | Produce an unpacked application directory |
| `corepack yarn dist:win:beta` / `dist:mac:beta` / `dist:win-portable:beta` | Produce platform release artifacts |
| `DSH_PACKAGE_ARCH=arm64 corepack yarn dist:win:stable` | Produce an experimental Windows ARM64 installer (x64 by default; a cross-arch build skips the smokes that can only run on this host) |

Conventions:

- Root `build`, `dev:*` and `dist:*` run `corepack yarn market:check` first: it verifies offline that the committed `dshmarket` version, lockfile and compatibility patch agree, without reaching the network or rewriting manifests. Moving the pin requires a human to run `corepack yarn market:prepare` and commit the version, lockfile and patch together.
- `nonead-dsh-desktop` and `dsh-plugin-desktop-beta` are **separate workspaces**: shared changes must land in both while preserving their declared differences; run `corepack yarn check` and each workspace check before release.
- After editing `README*.md` or `CHANGELOG*.md` in any language, refresh the Git blob hashes in the matching `*.i18n.yaml` (take them with `git hash-object`), otherwise `check:bilingual-docs` fails.
- `corepack yarn check:layout` needs an initialised submodule; in a purely headless environment, validate business code with `typecheck` / `test` / per-workspace `check` instead.
- **CI must not let the code under review decide what runs**: the `changes` job restores `scripts/` from the **pull request base** before running the classifier and the documentation/market gates (documents still come from the working tree); `workflow_dispatch` has no base, so it falls back to the head copy with a warning. CI runs `corepack yarn check:ci` (= local `check` without `verify:aa`) instead of rewriting `dsh-plugin-desktop-beta/package.json` at run time.
- **Version parity is part of the gate**: `scripts/verify-layout.mjs` requires both workspaces' `version` to equal the newest `## <version> — <date>` heading in `CHANGELOG.md`, so missing either side on a release fails.

<a id="release"></a>

## Release and updates

- **Two product lines**: produced by the two desktop workspaces. Beta and stable installers differ in bundle id, artifact prefix and update channel and must not be mixed.
- **Channel protocol**: the version check requests `https://www.nonead.com/software/ndsh-desktop/version`, reporting the current version in `X-DSH-Desktop-Version`, `stable` / `beta` in `X-DSH-Desktop-Channel`, and a locally generated, persisted random UUID in `X-DSH-Desktop-Installation-Id`. Installer downloads carry `channel` and `X-DSH-Desktop-Target-Version` but never the installation id or the current version.
- **Channel enforcement**: the server response must echo the channel; the stable channel accepts only plain SemVer while the Beta channel accepts only `-beta.N`, and the client never silently downloads across channels.
- **Version consistency**: the uploaded artifact, the bare download URL's version-to-file mapping and the version reported by the endpoint must all match — a mismatch surfaces as a 404 rather than a wrong install.
- **Release prerequisites**: run `corepack yarn aa:prepare-release` first; if this release ships a new `dshmarket`, a human must also run `corepack yarn market:prepare` and commit it. The Windows distribution commands additionally verify AA artifacts with `--verify-release`.

<a id="plugins"></a>

## Plugin ecosystem

Plugins extend DSH — models, tools, UI and workflows are all plugins that compose like building blocks. Nonead DSH Desktop does not modify upstream source and is not a hard-coded shell: the pinned upstream runs as-is, and the desktop shell itself plugs in through the same "everything is a plugin" rule.

Plugin authors only need three things:

1. **Ordinary DSH plugins** are developed exactly as in any DSH environment — see [plugin development](docs/plugin-development.en.md).
2. **Desktop services** (`desktopProfiles`, `desktopPnpm`, …) let plugins inspect or switch profiles and install, update or remove plugins — see [desktop plugin services](dsh-plugin-desktop-beta/docs/plugin-services.md).
3. **Composition and patches**: a profile is composed by stacking patch layers, where `id` matches an existing row and `insert` appends new rows; mind the three "silently inert" failure modes in [Security boundaries](#security).

The vision and three principles are in the [DSH plugin ecosystem proposal](docs/plugin-ecosystem.en.md); the community proposal for a unified plugin contract is [Community Fabric](dsh-community-fabric/README.md).

## Relationship to upstream

Nonead DSH Desktop is an independent community project built on [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) and the Cordis plugin model, developed and maintained by **Nonead Corporation**.

Upstream provides the core agent capabilities, plugin system, Web UI and runtime packages. This repository owns:

- Desktop application packaging (Electron main process, windows, tray, menus, materials)
- Starting, stopping and recovering the local Host service, including crash fallbacks
- Profiles and patch layers, the first-run wizard, browser and LAN access control
- Shipping the plugin market and the brand skin inside the installer
- Windows / macOS / Linux builds, signing and release flow, and auto-update

If you only want to use DeepSeek Harness from the command line, or want to work on its core, go to the upstream repository instead.

<a id="limits"></a>

## Known limitations

- **In-app update on Linux only checks the version** and never downloads an installer; upgrade by downloading a fresh AppImage.
- **Windows ARM64 ships as an experimental build**: `dist:win:stable` produces only the x64 installer by default; arm64 requires `DSH_PACKAGE_ARCH=arm64` (pair it with `DSH_PACKAGE_OUTPUT_DIR` for a separate output directory). The shell is native arm64 while the bundled runtime stays on the x64 payload (Windows emulation), a cross-arch build skips the run-only smokes, and the update channel currently carries a single `windows` artifact, so it cannot serve x64 and arm64 side by side.
- **Windows installers are not cryptographically verified yet**: the download path supports a server `installerSha256`, but the version endpoint does not publish it, so only `ProductName` / `ProductVersion` are compared for now (Stable shell only; the Beta shell checks just the installer magic bytes and size, then executes it).
- **LAN access has no authentication** — it hands this machine's DSH to everyone on the same network segment.
- **A wrong plugin `inject` service name fails silently** as a permanently pending plugin, showing up only as HTTP 4xx.
- A local `yarn install` may rewrite the `dsh-nonead-client-skin` content fingerprint in `yarn.lock` (not reproducible across machines); **do not commit such local lockfile changes**.
